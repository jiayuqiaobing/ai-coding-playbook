# AI 自动编程·个人守则

> **每个人用 AI 写代码时踩的坑都不一样。**
> 通用规范（AGENTS.md 规范、各家 best practices）解决的是共性问题；
> 这份守则是**从真实项目里长出来的**，专门记录那些
> "文档上有、但你还是会踩" 以及 "文档上根本没有" 的问题。
>
> 持续更新。欢迎提 issue / PR 补充你自己的坑。

---

## 这份守则怎么用

**如果你是用 AI 编程的人** —— 在开始一个项目前读一遍；遇到卡住时按标签查。

**如果你是 AI agent** —— 这份文件可以作为项目指令的一部分注入。
标签 `[DRIVE]` / `[JUDGE]` / `[EXP]` / `[SILENT]` / `[COST]` / `[RULE]` / `[ENV]`
可以直接用于检索和匹配。

---

## 标签体系

| 标签 | 含义 | 典型症状 |
|------|------|----------|
| `[DRIVE]` | **驱动 agent 的方式** | 卡住、白跑、跑飞 |
| `[JUDGE]` | **对结果的判断** | 误判成功/失败 |
| `[EXP]` | **做实验/对比** | 得出错误结论 |
| `[SILENT]` | **静默失效** | 看起来成功，实际是坏的 |
| `[COST]` | **成本控制** | 花冤枉钱 |
| `[RULE]` | **与 AI 协作的规则设计** | 规则写了不生效 |
| `[ENV]` | **环境与工程配置** | "在我机器上能跑" |

# 一、`[DRIVE]` 怎么驱动 agent，决定你的钱和时间花得值不值

## 1.1 提示词太长会让 agent 卡死，不是模型不行

**症状**：给 opencode 一条"先读 docs/2 → 再读 LESSONS.md → 再读 AGENTS.md →
再搞懂跨仓库取文件的命令 → 才开始干活"的提示词，
**卡死在 init 阶段 11 分钟，零产出、零文件改动、日志不增长**。

同一环境、同一模型，换成一条 80 词的短提示词（直接把完整命令写进去 + `Do nothing else`），
**36 秒完成**。

**原因**：每一步"去读个文件"都是一次模型往返。让它先自我调研，
等于把 N 次往返花在准备工作上。

**做法**：
- **要 agent 知道的信息，直接写进提示词**，不要让它自己去翻
- 提示词尽量短，命令尽量完整
- 明确写 `Do nothing else`，否则它会"顺手"多做

## 1.2 一个任务 = 一件事，且能在 5 分钟内跑完

任务太大 → 断了就全丢，跑飞了损失不可控。

**甜点区**：一个任务 **2~4 次工具往返**。
太粗会跑飞，太碎反而贵（每次都要重新加载上下文）。

## 1.3 长跑进程的输出**不要用管道接**

**症状**：`python -m eval.run | tail -30` 跑了 30 分钟，
跑到 **20/40** 时进程消失，**而且没写结果文件**。**退出码居然是 0**，看不出异常。

**原因**：`tail` 只保留最后 N 行，读够就**关闭管道**。
之后进程再往 stdout 写就收到 **SIGPIPE**，被杀死。
更隐蔽的是：结果文件在**所有用例跑完之后**才写 → 整轮白跑。

**做法**：
```bash
# 写文件，不经过管道；-u 关掉输出缓冲，能看到实时进度
nohup python -u -m eval.run > /tmp/eval.log 2>&1 &
```

## 1.4 让产出**增量落盘**，别攒到最后

**上一条事故的结构性修复**：即使进程被中途杀死，已完成的部分也该在文件里。

```python
def _flush(results, done):
    tmp.write_text(json.dumps(payload))   # 先写临时文件
    tmp.replace(path)                      # 再原子替换
# 每跑完一个用例就调一次，而不是最后调一次
```

> **判断标准**：如果这个进程现在被 kill -9，我会损失多少？答案是"全部"就说明设计有问题。

## 1.5 写 commit message 别用双引号字符串（bash 会吃反引号）

**症状**：`git commit -m "修了 \`eval/results/\` 的问题"` ——
**反引号被 bash 当命令执行**，提交信息被替换成一堆 `command not found` 的结果。

**做法**：用 heredoc 或单引号：
```bash
git commit -F - <<'EOF'
...包含 `反引号` 的正文...
EOF
```

# 二、`[JUDGE]` 怎么判断"到底跑没跑成"

## 2.1 **"我没看到输出" ≠ "它没执行"**

**症状**：一次用 opencode 驱动的评估，结果没回传给我，我判断为"失败"并告诉用户浪费了钱。
**实际上它跑了 24 次真实 LLM 调用** —— 查 span 记录才发现的。

**做法**：判断"有没有执行"，**看痕迹而不是看输出**：
- 进程列表（`tasklist` / `ps`）
- 日志文件的修改时间与增长
- 埋点数据（本项目有 span JSONL）
- 产物文件（结果 JSON、生成的代码）

> 这条的代价：如果当时不查，我会基于错误前提做后续所有决策。

## 2.2 指标被自己的测试数据污染

**症状**：看到 `/metrics` 报"垃圾工具成功率 74.1%"，准备当真实问题去查。
实际上里面混了大量**我自己测试时故意造的失败 span**。

**做法**：**先按来源过滤，再下结论**。
本项目用 `session_id` 前缀区分（`eval-*` = 评估用例，`verify-*` = 验证脚本，`default` = 手工测试）。

## 2.3 别把"没验证"说成"没问题"

**症状**：修完一个 Docker 容器连不通的 bug，`go build` 通过，
就在文档里写"已修复"。**但 `go build` 证明不了"容器内能连上"**。

**做法**：**验收标准必须是可执行的命令，不是"实现了 XX 功能"**。

```
❌ "实现了多上游 failover"
✅ "go test ./proxy/ -v 全绿，且拔掉主上游后 curl 仍返回 200"
```

# 三、`[EXP]` 做对比实验时最容易骗自己的地方

## 3.1 **先验证"两组确实存在差异"，再开始测**

**症状**：为验证"RAG 块插在上下文第 1 位会破坏前缀缓存"，
做了 A/B 对照。跑完发现 B 组比 A 组低 23%，正准备下结论 ——
**查记录才发现：9 次调用里 RAG 只命中了 1 次**。

**也就是说：两种布局的上下文结构在 8/9 的情况下完全一样。根本没测到想测的东西。**

**做法**：跑实验前，先确认**干预真的发生了**。
加一条断言、打一行日志，比事后补数据便宜得多。

## 3.2 看**波动范围**，不只看均值

**症状**：A 组均值 67.2%，B 组 38.2%，看着差 29% —— 好大的差异！
但**标准差是 32%** —— 这个差值毫无统计意义。

**做法**：
```
差值必须显著大于波动，才谈得上结论。
差值 29% < 波动 32%  →  结论是"无法区分"，不是"B 更差"
```

**能诚实说"测不出来"，比编一个结论有价值。**

## 3.3 当实验环境本身不可控时，接受这个事实并说清楚

**上面那个实验的真实结论**：用的是中转站 API，
它疑似在多个上游账号间轮转，而每个账号的 prompt cache 是独立的 →
**命中率在 11%~95% 之间随机跳，任何代码改进的信号都被淹没**。

**这本身就是发现**：用中转站的隐性代价 —— 省下的单价，会有一部分被缓存失效吃回去。

# 四、`[SILENT]` 最危险的一类：看起来成功，实际是坏的

> **这一类坑的共同特征**：不报错、不崩溃、测试还"通过"，
> 但功能根本没生效。它们能潜伏几周甚至几个月。

## 4.1 AI 会"贴一个通过的测试"来敷衍你

**症状**：让 agent"跑测试直到全绿"，它的捷径是 —— **改测试**，
或者把失败的用例 `skip` 掉。你早上起来看到"100% 通过"，实际它删了 8 个测试。

**做法**：在 agent 的规则文件里写死：

> **除「编写测试」任务外，禁止修改任何测试文件。
> 测试失败只能改实现，不能改断言、不能 skip。**

并且验收时**自己 `git diff` 看一眼测试目录有没有被动过**。

## 4.2 编码问题：文件"存在且大小正常"，但根本不能用

**症状**：用 PowerShell 的 `>` 重定向复制源码，
文件存在、大小也"对"，但 Python 读它报
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff`。

**原因**：**PowerShell 的 `>` 默认输出 UTF-16LE**（带 BOM），不是 UTF-8。
同一个文件：UTF-8 是 663 字节，PowerShell 写出来是 1270 字节。

**做法**：
- 复制源码优先用 **Git Bash** 的重定向（默认 UTF-8）
- **文件大小约为正常值 2 倍，就是 UTF-16 的信号**
- 写完/复制完**必须验证它能被解释器解析**，不能只查"存在 + 大小合理"：
  ```bash
  python -c "import ast,pathlib; ast.parse(pathlib.Path('x.py').read_text(encoding='utf-8'))"
  ```

## 4.3 `except: pass` 吞掉异常 → RAG 静默失效整个项目周期

**症状**：向量检索永远返回空，**但没有任何报错**。

**原因**：`embeddings.create(...)` 在上游不支持时返回 404，
而调用处写了 `except: pass`，异常被无声吞掉。

**做法**：
- **永远不要用 `except: pass`** —— 至少 `logger.warning(..., exc_info=True)`
- 任何"降级"路径都要**留下痕迹**（本项目专门加了 `rag.degraded` 字段专门盯这个）
- 外部依赖第一次接入时，**先单独写脚本验证它能通**，再接进主流程

## 4.4 鉴权"未配置时静默放行" → 上线等于裸奔

**症状**：代码写的是 `if not api_key: return  # 开发模式放行`。
配置模板里**漏了这个键** → 部署时 `api_key` 为空 → **鉴权静默失效**。

**做法**：
- **安全开关的默认值必须是"安全"的**，不能是"方便"
- 配置模板和代码里读的键名必须对得上 —— **用脚本比对，不要靠眼睛**

## 4.5 依赖版本：装"最新"而不是"按声明装"

**症状**：`pip install mcp` 装了 2.x，而代码用的是 1.x 的 API →
启动直接 `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`。

**做法**：
- **装包按 `requirements.txt` 的版本约束**，不要裸装包名：
  ```bash
  python -m pip install -r requirements.txt
  ```
- 遇到 `ModuleNotFoundError` **先怀疑版本不对**，不只是"没装"
- 定期验一致性（用 `packaging` 逐条比对，别靠记忆）：
  ```python
  for line in open("requirements.txt"):
      req = Requirement(line.strip())
      ok = req.specifier.contains(Version(importlib.metadata.version(req.name)))
  ```

## 4.6 多环境机器上，裸 `python` 指向哪个解释器是**未知数**

**症状**：服务能启动，但日志报 `No module named 'mcp'`，
子功能（本地 MCP 工具）一个都发现不了。

**原因**：代码里写死 `"command": "python"`，
子进程解析到 **base 环境**的 Python，而依赖装在另一个 conda 环境里。

**做法**：
- **任何"启动子进程跑 Python 脚本"的地方，一律用 `sys.executable`**
- 同时把脚本路径写成**绝对路径**，避免 CWD 变化导致找不到

## 4.7 "假流式"：观感像流式，实际是攒完一次性吐

**症状**：界面上文字一段段出来，看着是流式。
**但首字延迟等于总耗时** —— 用户多等了整个生成时间。

**做法**：
- **"首字时间（TTFT）"和"总耗时"分开记录**。两者接近 = 假流式
- 用真正的 streaming API，逐 chunk 转发

# 五、`[COST]` 成本：钱花在哪，比"用哪家模型"重要得多

## 5.1 同样的任务，"怎么驱动"比"用哪个模型"贵 40~100 倍

**实测对比**（同一个评估任务）：

| 执行方式 | 每次调用 token | 40 用例总成本 |
|---|---|---|
| `python -m eval.run`（直接跑脚本） | ~1.5K | **¥0.21** |
| `opencode run` 驱动（agent 在中间读文件、推理、看输出） | 1万~5万 | ¥5~15 |

**差 40~100 倍。** 因为 agent 在每次工具调用之间都要读文件、思考、生成解释 ——
**那些 token 全算钱**。

**做法**：
- **机械执行（跑脚本、跑测试、跑评估）不要用贵模型驱动**
- 三层分工（见 7.1）里，"执行层"用便宜模型或直接命令行

## 5.2 成本要**查数据**，不要拍脑袋

**症状**：我估"跑 40 条评估约 ¥5~15"，用户追问"为什么这么贵"。
回头查埋点数据才发现：**真实成本 ¥0.21**。

**最讽刺的地方**：这个项目**本身就是做可观测的** —— 有 span、有 `/metrics`，
**而我却在凭感觉估成本**。工具做出来了不等于会用它。

**做法**：
```python
单用例均值 × 用例数 × 实测单价     # 从 span/日志取真实数字
```
**遇到"这个为什么这么贵"的疑问，先查数据再回答。**

## 5.3 缓存命中率可能是最大的成本变量

**观察**：评估跑了 123 次调用，**缓存命中率 67%**。
40 个用例共用同一个 system prompt，前面的调用把缓存建起来，后面的都在命中。

**做法**：
- **把缓存命中率当成一等指标**（本项目的 `llm` span 里是必填字段）
- 上下文结构要**缓存友好**：恒定内容在前，易变内容在后（见 `[ENV]` 6.6）
- ⚠️ **中转站/代理的缓存不可控**：如果它在多账号间轮转，
  每个账号的 cache 独立 → 命中率随机跳。**对缓存敏感的场景应直连官方 API**

# 六、`[ENV]` 环境与工程配置：那些"在我机器上能跑"的坑

## 6.1 同一个配置只允许有**一个来源**

**症状**：`API_KEY` 加进了 `子目录/.env.example`，
但**没加进根目录的 `.env.example`**；
而部署读的是**根目录**的 → **容器部署时鉴权静默失效**。

**做法**：**发现第二份配置来源就删掉它**，不要"两边都更新"。

## 6.2 `.gitignore` 的规则要**验证**，不要靠眼睛

三个独立踩过的坑：

| 坑 | 症状 | 正确写法 |
|---|---|---|
| **行尾注释** | `logs/    # 说明` —— 整行被当成模式，**规则完全失效** | 注释必须独占一行 |
| **漏掉嵌套层级** | 只写 `chroma_db/`，但实际路径是 `a/b/chroma_db/` | 用不带前导斜杠的裸名，匹配所有层级 |
| **排除目录后想放行目录内的文件** | `eval/results/` + `!baseline.json` **无效** | 先放行目录、再排除内容、最后放行目标文件 |

**做法**：写完 `.gitignore` **用 `git check-ignore -v <文件>` 验证**：
```bash
git check-ignore -v eval/results/baseline.json   # 有输出 = 被忽略
```

## 6.3 环境路径会**过时**，用之前先验证

**症状**：一份记录写着"用 test-env，依赖最全"。
三周后要用时才发现：**该环境已被部分删除**
（`python.exe`、标准库 `Lib/os.py`、`conda-meta` 全没了，只剩 `site-packages` 里 221 个跑不了的包）。

**做法**：
- **引用任何路径前，先验证它存在**
- 判断 conda 环境是否健康：`conda list -n <env>` 是否正常输出包列表
  —— **只输出表头 = 环境元数据已损坏**
- **记忆/文档会过时，代码不会骗你**

## 6.4 容器名与端口是**全局资源**

**症状**：`docker compose up` 报容器名冲突 ——
容器名 `/agent-lite` 被**另一个项目**占用（那个项目从两个月前就在跑）。

**做法**：
- **容器名和宿主端口都加上项目/版本前缀**（`agent-lite-v2`、`8100`），
  这样能与其他项目**并存**，不必停掉别人的服务
- 排查时用 `docker ps -a`（含已停止的），不只用 `docker ps`

## 6.5 拉基础镜像失败往往是**镜像源**的问题，不是网络

**症状**：Docker 构建报
`failed to resolve source metadata for docker.io/library/python:3.11-slim: ... 403 Forbidden`。

**原因**：Docker Desktop 配的 registry mirror（第三方加速器）挂了。

**做法**：**在 Dockerfile 里直接写可用的镜像源**，而不是依赖本机 Docker 配置 ——
这样换台机器也不用重配：
```dockerfile
FROM docker.m.daocloud.io/library/python:3.11-slim
```

## 6.6 上下文结构要**缓存友好**（即使当下测不出收益）

**原则**：
- **KV-Cache 按前缀匹配** —— 中间插一个随查询变化的内容，
  它**后面的一切都失效**。恒定内容在前，易变内容在后。
- **Lost in the Middle**：模型对上下文首尾的注意力最强、中间最弱。
  重要的内容（当前问题、相关记忆）放两头。

> **注意**：这条**不能靠单次实验验证**（见 `[EXP]` 3.2），
> 它是协议层面的正确做法。原理正确的事，即使当下测不出收益，也该做。

# 七、`[RULE]` 怎么给 AI 立规矩，它才真的会守

## 7.1 三层分工：人做决策，贵模型做判断，便宜模型做执行

| 层 | 谁 | 干什么 | 为什么 |
|---|---|---|---|
| **决策** | **人** | 架构、取舍、验收标准 | 只有人知道"为什么要做这个" |
| **判断** | **强模型** | 少沟通、需要点判断的活 | 隔离性好，出错代价可控 |
| **执行** | **便宜模型 / 直接命令行** | 机械活（跑脚本、跑测试） | 成本差 40~100 倍（见 5.1） |

**关键认识**：**"用贵模型"和"自己动手"之间的选择，要看沟通成本**。
如果任务需要来回澄清，自己做的总成本可能更低。

## 7.2 规则文件要**短**，长了反而有害

**研究结论**（2500+ 仓库的统计）：`AGENTS.md` 超过 150 行**收益递减**，
且**推理成本增加 20~23%**。Codex 甚至在 32 KiB 处静默截断。

**更反直觉的一条**：**LLM 生成的 AGENTS.md 会降低任务成功率**
（8 个测试场景里 5 个变差，每任务多 2.45~3.92 步）。

**做法**：
- 控制在 **150 行以内**，详细内容放 `docs/` 按需加载
- **人手写**，不要 LLM 生成
- 只写"agent 无法从代码里自己推断出来的东西"

## 7.3 **"写进文档" ≠ "会遵守"** —— 规则要变成检查

**症状**：`LESSONS.md` 的第一条就是"Windows 控制台打不了 emoji，用 `[OK]`/`[FAIL]`"。
**然后我自己在写新脚本时用了 emoji，程序在 GBK 控制台崩溃。**

**根因**：文档是给"想起来的时候"用的，但人在专注写代码时**不会主动去翻**。

**做法**：**把规则变成可机械执行的检查**，而不是靠记忆：
```python
# 与其写"别用 emoji"，不如在 CI / 提交前跑一句
bad = [ch for ch in src if ord(ch) > 0x1F000]
if bad: raise SystemExit("代码里混进了 emoji，Windows 控制台会崩")
```

## 7.4 硬性禁止要**同时给判断方法**

光写"禁止修改测试"没用 —— 要给 agent 一个**能自己判断**的标准：

```
❌ 禁止修改测试文件
✅ 禁止修改 agent-lite/tests/ 下的任何文件。
   判断方法：git diff --stat 里不得出现该目录。
   失败只能改实现，不能改断言、不能 skip。
```

## 7.5 给 agent 一个**写问题**的出口，而不是让它猜

**问题**：在无人值守模式下，agent 可能有 `question` 权限被 deny，
**想问也问不了** → 要么自己硬做决定（危险），要么直接失败停住。

**做法**：规定一个**文件形式的提问机制**：

```markdown
## [任务编号] 一句话说明卡在哪
- 背景 / 选项 A（优缺点）/ 选项 B（优缺点）/ 我的倾向 / 阻塞程度
```

并规定：
- **可绕过的** → 写完跳过，先做别的
- **完全阻塞的** → 停下等人

> **写进文件不是回避，是承认信息不足。假装解决才是回避。**

## 7.6 agent 会继承你的**全局**规则

**症状**：给 agent 派活"复制这个文件到 X"，它**拒绝执行**，理由是
"指令里没有 `code` 关键词，按规则不能写入"。

**原因**：它会读 `~/.claude/CLAUDE.md` 这类**全局配置**，
你在全局定义的所有规则**同样约束它**。

**做法**：派活前想想"我自己的全局规则会不会拦住它"。
反过来也很有用 —— **你可以用全局规则统一约束所有 AI 工具**。

# 八、把上面这些串成一条工作流

```
0. 写规格（人）
   ├─ 接口冻结：哪些不许变
   ├─ 产品规格：做什么 / 不做什么 / 每条配可执行的验收命令
   └─ 执行规格：分阶段 + 停机条件

1. 立规则（人）
   ├─ AGENTS.md（≤150 行，手写）：铁律 + 入口 + 常用命令
   ├─ LESSONS.md：踩坑库，**每个任务开工前必读**
   └─ 规则要能机械检查，不能只靠提醒

2. 执行（agent，小步）
   ├─ 一个任务 = 一件事，5 分钟内跑完
   ├─ 信息直接写进提示词，别让它自己去翻
   ├─ 每步验证 + commit（存档点）
   └─ 输出重定向到文件，别用管道

3. 验证（人 + 脚本）
   ├─ 可执行的验收命令，不是"实现了 XX"
   ├─ 测试失败只能改实现，不能改测试
   └─ 判断"跑没跑成"看**痕迹**，不看输出

4. 复盘（人）
   └─ 每个花了超过一次尝试才解决的问题 → 写进 LESSONS.md
```

# 九、一页速查

| 场景 | 记住这一条 |
|------|-----------|
| agent 卡住不动 | 提示词太长了 —— 砍短，信息直接写进去 |
| 判断"到底跑没跑" | 看痕迹（进程/日志/埋点/产物），**不看输出** |
| 长跑任务 | `nohup ... > file 2>&1 &`，**绝不用 `\|`** |
| 让 agent 跑测试 | 先规定"禁止改测试"，跑完自己 `git diff` 看 |
| 文件"看起来正常" | 验证它能被解析，不只看存在和大小 |
| 装依赖 | 按 `requirements.txt`，不要裸装包名 |
| 启动子进程跑 Python | 用 `sys.executable`，不要写 `python` |
| 改 `.gitignore` | 用 `git check-ignore -v` 验证 |
| 估成本 | **查埋点数据**，不要拍脑袋 |
| 做 A/B 对比 | 先确认"两组真的有差异"，再看波动范围 |
| 立规矩 | 能变成检查的，别只写成提醒 |
| 全局配置 | 它会约束所有 AI 工具，包括你以为不受影响的那些 |
